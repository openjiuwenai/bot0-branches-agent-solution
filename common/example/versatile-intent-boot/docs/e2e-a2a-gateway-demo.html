02 双模 Agent 接入 · 高码与低码共存

整套体系围绕 openjiuwen runtime 的单槽位 SPI AgentHandler 展开。既能接入高码 Agent（基于 openjiuwen runtime，业务逻辑写在 Java 代码里），也能接入低码 Agent（Versatile，业务逻辑配在可视化工作流里）——两者跑在同一套 runtime 上，层间用同一套 A2A 协议与 agent card 寻址互通。

07 FAQ · Versatile 如何接入与配置

会议中常被问到的注入与配置问题，附关键文件:行号便于现场追源。

Q1Versatile 服务是怎么接入的？真实 Versatile 和 Mock 如何切换？

接入入口是 VersatileIntentAutoConfiguration，它用 @ConditionalOnProperty(prefix="openjiuwen.service.versatile", name="url-template") 守门——只有配了 url-template 才会注册 AgentHandler，否则所有 query 返回 503。

versatile.url-template 是真实 Versatile 的 SSE 端点模板：http://{host}/v1/{project_id}/agents/{agentId}/conversations/{conversation_id}，占位符运行时填充。

本演示不连真实 Versatile，而是用 MockVersatileController 模拟：@Profile("mock-versatile") 激活，暴露与真实 Versatile 同构的 POST /v1/proj/agents/{agentId}/conversations/{conversationId}，返回 text/event-stream。e2e 脚本把每个进程的 url-template 重写为指向本进程该端点，于是整条链路在本地跑通。

源：VersatileIntentAutoConfiguration.java:37 · MockVersatileController.java:45,68 · application-dev.yml:4

Q2两层意图是怎么映射到下一层 agent card 的？

两层映射各司其职：

  • intent-agent-mapping（意图 → agentCard）：application-layer1.yml:28-38 定义 intent_L1_hotel → agent_card_L2_hotel 等；application-layer2.yml:26-33 定义 intent_L2_hotel_domestic → agent_card_biz_hotel_domestic。downstream 业务层不配此映射。
  • card-resolver.local-mapping（agentCard → 物理地址）：application-mock-versatile.yml:13-27 定义 agent_card_L2_hotel → localhost:8082、agent_card_biz_hotel_domestic → localhost:8083。由 LocalMappingCardRegistrar 注册成临时 AgentCard 供路由。

Versatile 返回的三字段 SSE（response_content / intent_id / agent_id）经 Adapter 解析后，命中上面的 mapping 决定下一跳。

Q3「订酒店」「意图不明」这些 mock 应答数据写死在哪？

全部在 MockVersatileController 的 canned SSE 里，按 (agentId, query关键字, hasAssistant) 三元分流：

  • agent_L1 + 「订酒店」→ agent_id=agent_card_L2_hotel（第 176-180 行）
  • agent_L2 + 「订酒店」→ agent_id=agent_card_biz_hotel_domestic（第 181-186 行）
  • agent_biz → 业务结果「酒店预订成功：上海今晚五星」（第 187-190 行）
  • agent_L2 + 「意图不明」+ 首调 → intent_id=1，无 agent_id（第 262-266 行）——触发自消或重识别
  • agent_L1 + 「意图不明」+ hasAssistant=true（reclassify 重试）→ 直接 agent_card_biz_hotel_domestic 跳过 L2（第 243-249 行）

切真实环境后这些 mock 不再生效，应答由真实 Versatile 工作流产出。

Q4A2A Gateway 模式怎么开？header 透传做了什么？

总开关 openjiuwen.service.a2a-gateway.enabled=true（A2AGatewayAutoConfiguration.java:35）。开启后走 A2AGatewayRemoteAgentCaller，关闭（默认）走 LocalHttpRemoteAgentCaller，二者互斥。

本演示用 a2a-gateway-test profile 覆盖：base-url=http://localhost:8084、token=dev-token、version-node=v1、streaming=false（application-a2a-gateway-test.yml:10-16）。注意 profile 顺序：必须在 mock-versatile 之后激活，因为后者把 enabled 设为 false，靠后激活覆盖。

Header 透传（A2AGatewayRemoteAgentCaller.buildHeaders 第 274-303 行）：token / userId / versionNode 来自配置与请求元数据；X-B3-TraceId / X-B3-ParentSpanId / X-B3-Sampled / X-Biz-Tag 从上游 HTTP request 透传，X-B3-SpanId 每跳新生成——这就是日志里能验证全链路 trace 的原因。

⚠ streaming 必须与对端网关匹配：只支持 sync message/send 时必须 false，否则 SDK 等不存在的 SSE 流直到超时。

Q5route-cache / reclassify / direct-chain 三个特性怎么开？

各自独立的 *Properties + @ConditionalOnProperty，互不耦合：

特性开关关键参数
路由缓存versatile.route-cache.enabledttl 默认 30m
回退重识别versatile.intent-reclassify.enabledmax-reclassify 默认 1 · ambiguous-intent-id 默认 "1"
直链透传example.direct-chain.enableda2a-forward-agent-cards · timeout 默认 600s

演示中 L1 默认开 route-cache + reclassify；Round 3 额外开 direct-chain，靠 AutoConfig 顺序自动顶替 route-cache（见 Q6）。

Q6为什么说 AutoConfiguration 顺序是「load-bearing」？

AgentHandler 槽位用 @ConditionalOnMissingBean 先到先得，META-INF/spring/...AutoConfiguration.imports 的排列顺序决定谁先抢到：

1 DirectChainAutoConfiguration ← direct-chain.enabled=true 时抢占
2 RouteCacheAutoConfiguration ← route-cache.enabled=true 时抢占
3 VersatileIntentAutoConfiguration ← bare handler，仅 route-cache.enabled=false
4 A2AGatewayAutoConfiguration ← 先于 runtime 的 A2AAutoConfiguration 注册 caller
5 ReclassifyAutoConfiguration

所以 Round 3 里 开启 direct-chain 会自动顶替 route-cache，无需手动关 route-cache.enabled。新增 AgentHandler 变体时，必须在此文件中排在 VersatileIntentAutoConfiguration 之前，并配 @ConditionalOnMissingBean。

Q7直链 direct-chain 的 X-Direct-Chain 隧道是什么？

DirectChainVersatileAgentHandler 包装 base handler，复用其意图识别与 a2a_delegate 生产，但截胡 delegate：一旦命中 shouldDirectChain(agentName)，直接经 gateway 隧道 POST 到目标 versatile 端点，附带 X-Direct-Chain: true 头（常量 DIRECT_CHAIN_HEADER），回传的原始 data: 行以 TYPE_CHUNK 透传给 client。

所以 client 收到的是业务原始 versatile SSE（custom_rsp_data），没有 a2a JSON-RPC 的 TASK_STATE_COMPLETED 折叠——这就是 Round 3 验证的核心。

源：DirectChainVersatileAgentHandler.java:110-129（doDirectChain）· DirectChainProperties.java:61-63（shouldDirectChain）

Q8切到真实 Versatile 环境要改哪些配置？

核心是换 profile + 换 url-template，其余配置与 mock 无关：

  1. 去掉 dev、mock-versatile profile → MockVersatileController 自动失效。
  2. 设置真实 versatile.url-template，把 host / project_id 换成真实值（此属性是 handler 注册的必备触发条件）。
  3. 移除 card-resolver.local-mapping 的 localhost 映射。走 Gateway 模式就配真实 a2a-gateway.base-url + token（token 必填，缺失 fast-fail）；走 local-HTTP 模式就提供真实 agentCard→URL 映射或让 runtime 走真实 card 发现。
  4. feature 开关（route-cache / reclassify / direct-chain）保持不变，与 mock 无关。
  5. 按真实网关能力设 streaming（支持 SSE 流保持 true，否则 false）。

一句话：profile 从 dev,mock-versatile,layerX 改为 layerX，url-template 指向真实 Versatile 端点即可。
