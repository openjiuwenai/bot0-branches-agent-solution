Agent-as-Judge — D1: Bundle Skills & Agent-Executed Scripts

A spec for extending the shipped agent-as-judge evaluator so judging skills ship as directory bundles (SKILL.md + scripts/ + assets/), stored in a per-(preset, dimension) DB, loaded per evaluation, and executed by the judge agent itself.

Status: spec, not yet implemented Phase D1 Owner: evo_agent / agent-judge Date: 2026-08-14

01What exists today (the shipped feature)

The agent-as-judge evaluator is live behind POST /evaluate/agent-judge. A request selects a preset (a named bundle of dimensions + weights + runtime); for each dimension it spawns one bounded, non-interactive coding-agent subprocess (claude or codex) that judges that single dimension, returning a DimensionJudgment{dimension, score, reasoning}. An LLM aggregator then fuses the verdicts into overall_score + plural skill_attributions.

Today a "skill" is a single bundled .md doc copied from the package (helper_skills/*.md) into the judge workdir; the agent Reads it as reference. There is no script or asset concept on the evo path.

02What D1 changes, in one paragraph

A skill becomes a directory bundle — SKILL.md (manifest) + scripts/*.py + assets/*. Bundles are uploaded (trusted-internal only) into an evo-side sqlite DB keyed by (preset, dimension). On each evaluation the relevant bundles are materialized into the judge workdir; the SKILL.md tells the agent which scripts/assets are available, and the judge agent executes the scripts itself using its native bash/python — including a bundle weight-script that produces overall_score.

03Locked decisions (with rationale)

Decision · Skill shape

Skill = directory bundle: SKILL.md + scripts/ + assets/. This convention already exists in the agent-core ecosystem (openjiuwen/.../skill_evaluator/skills/skill_tester/ has SKILL.md + scripts/run_eval_query.py). Reusing it keeps the door open to interop; SKILL.md as manifest lets the agent discover what to run.

Decision · Storage

New evo-side sqlite DB (skill_store), keyed by (preset, dimension?), mirroring the existing control_store.py pattern (sqlite3 + frozen dataclass + content_hash, no ORM). Not the Adapter sidecar's skill store — adapter skills are the evaluated agent's capabilities; judging rubric-skills are a different concept and must not be conflated.

Decision · Execution model

The judge agent runs the bundle scripts (claude/codex native bash/python). This reverses the earlier read-only pin: claude leaves --permission-mode plan, codex leaves --sandbox read-only, and tool_allowlist gains Bash. The original Q1 constraint (bounded read-only judge) is deliberately abandoned for this feature.

Decision · No sandbox

Scripts run with no sandbox, in the judge subprocess with the agent's privileges. Acceptable only because upload is restricted to trusted-internal users. If that trust boundary ever opens to external upload, this becomes an arbitrary-code-execution surface and a sandbox must be added before relaxing it.

Decision · overall_score source

The attribution-phase weight-calculation script is a bundle script the agent runs; overall_score is agent-sourced. The in-code deterministic scorer (scorers.py, tc × Σweighted) is retired on the D1 path. The shipped feature keeps the in-code scorer until D1 lands, to preserve determinism during the transition.

Decision · Attribution

skill_attributions[] is still produced by the LLM aggregator. Only the overall score moves to an agent-run script; the LLM still attributes which skills contributed.

Consequence to carry

overall_score is no longer deterministic or reproducible. The agent may fail to run the weight script, run it wrong, or fabricate its output. The reliability guarantees built into scorers.py (clamp, fallback, tc-gating) do not apply on the D1 path. A possible (optional, not in scope) mitigation: make the weight script itself deterministic and constrain the agent's output schema to echo the script's raw stdout — then the code stays deterministic and the agent merely "runs and pastes."

05Phase 1 — storage + upload/management API

5.1  skill_store module (new)

New file src/evo_agent/evaluator/agent_judge/skill_store.py. Mirror control_store.py conventions: sqlite3, frozen dataclasses, content_hash for versioning/dedup, no ORM.

-- one uploaded bundle = one row
CREATE TABLE judge_skill_bundle (
  bundle_id    TEXT PRIMARY KEY,          -- uuid
  preset       TEXT NOT NULL,             -- "default" | "safety_focus" | "*"(global)
  dimension    TEXT,                      -- dimension name; NULL = preset-level global
  skill_name   TEXT NOT NULL,             -- bundle name (D4 namespace isolation)
  content_hash TEXT NOT NULL,            -- hash over all files; version/dedup
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,
  UNIQUE(preset, dimension, skill_name)   -- same slot re-upload = upsert
);
CREATE INDEX idx_bundle_lookup ON judge_skill_bundle(preset, dimension);

-- one file per bundle (SKILL.md / scripts/*.py / assets/*)
CREATE TABLE judge_skill_file (
  file_id   INTEGER PRIMARY KEY AUTOINCREMENT,
  bundle_id TEXT NOT NULL REFERENCES judge_skill_bundle(bundle_id) ON DELETE CASCADE,
  rel_path  TEXT NOT NULL,                -- "SKILL.md" | "scripts/weight.py" | "assets/rules.json"
  content   BLOB NOT NULL,
  UNIQUE(bundle_id, rel_path)
);

@dataclass(frozen=True)
class SkillBundle:          # metadata only
    bundle_id: str
    preset: str
    dimension: str | None
    skill_name: str
    content_hash: str
    created_at: str
    updated_at: str

@dataclass(frozen=True)
class SkillFile:
    rel_path: str
    content: bytes

class SkillStore:
    def __init__(self, db_path: Path) -> None: ...
    def upsert_bundle(self, *, preset: str, dimension: str | None,
                      skill_name: str, files: dict[str, bytes]) -> SkillBundle
        # transactional: drop old file rows for the slot, write new bundle+files, return with hash
    def bundles_for(self, preset: str, dimension: str) -> list[tuple[SkillBundle, list[SkillFile]]]
        # materialization lookup: (preset,dimension) ∪ (preset, dimension IS NULL)
    def list_bundles(self, preset: str, dimension: str | None = None) -> list[SkillBundle]
    def get_bundle(self, bundle_id: str) -> SkillBundle
    def get_files(self, bundle_id: str) -> dict[str, bytes]
    def delete_bundle(self, bundle_id: str) -> None

06Phase 2 — per-evaluation load + prompt/allowlist/runtime

6.1  Workdir materialization (agent_judge/workdir.py)

Add a new method. Keep the existing materialize_helper_skills — the bundled rubric guide still ships from the package; both coexist.

def materialize_bundle(self, skill_name: str, files: dict[str, bytes]) -> Path:
    """Write a whole bundle tree to workdir/<skill_name>/<rel_path>; return its dir."""
    root = self.path / skill_name
    for rel, data in files.items():
        (root / rel).parent.mkdir(parents=True, exist_ok=True)
        (root / rel).write_bytes(data)
    return root

07Constraints still in force

  • HTTP-only scope. Do not wire agent-as-judge into the optimization pipeline; training rollout / validation gates still use LLMEvaluator.
  • mypy strict on src/ (gate is mypy src/); tests are ruff-gated only (ruff check src/ tests/ + ruff format --check src/ tests/). Ruff line-length=100. types.py / config.py are leaf modules; optimizer_runner.py is the only orchestration entry — don't entangle.
  • Trusted-internal upload boundary. The no-sandbox agent-exec model is safe only while upload is internal. Do not relax without adding auth + sandbox.
  • Do not commit / push unless the user explicitly asks.
  • Credentials: judge subprocess auth is ambient (claude via its own login / ANTHROPIC_API_KEY; codex via OPENAI_API_KEY); the aggregator LLM is supplied per-request via llm_config.

08Open details to resolve at landing time

These four do not block Phase 1. Resolve each when you reach the code that needs it; flag the choice in the PR.

  1. claude execution mode. plan cannot run Bash. Candidates: acceptEdits (auto-accept edits, but Bash may still prompt), bypassPermissions (too broad), or a settings allow-rule. Lean: acceptEdits + --allowedTools Read,Grep,Bash. Verify against claude --help before committing — CLI flag shapes in runtime.py are module constants precisely so they can be corrected in one place.
  2. weight-script execution structure. Either (a) a dedicated scoring agent call that runs weight.py and returns its stdout, or (b) folded into the aggregator LLM call (LLM told to run it via Bash and paste stdout). Lean (a) — cleaner separation, doesn't muddy the attribution LLM.
  3. D4 namespace isolation rule. Enforce a prefix or a deny-list that prevents judging-skill names from colliding with adapter agent-capability skill names. Pick the concrete rule in Phase 1 validation.
  4. Upload auth. If the trust boundary stays internal, network-layer trust suffices for v1; otherwise add a token scheme before opening upload.
