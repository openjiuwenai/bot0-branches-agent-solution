## 一、当前引擎的适用性分析

### 1.1 引擎定位

当前引擎（`direct_calculator.py` + `batch_builder.py`）是一个**确定性批次级计算器**：

- 输入：原油品种 + 加工量 + 收率模式（减一线去向）+ 批次划分
- 输出：装置进出料流量、利用率、经济效益
- 特点：计算快、结果确定、缓存友好

### 1.2 适用场景

当前引擎在以下场景表现良好：

| 场景 | 适用性 | 原因 |
|------|--------|------|
| 常规月度排产求解 | ✅ 适用 | 单一收率模式，批次边界切换，满足基本业务 |
| 方案对比选优 | ✅ 适用 | 枚举 2^n 种组合，选收入最高的 |
| 快速效益估算 | ✅ 适用 | PASS 1 物理结果缓存，秒级返回 |
| 停工折算 | ✅ 适用 | 按小时比例线性缩减，逻辑简单有效 |

### 1.3 不适用场景（4 个核心短板）

#### 短板 1：减一线切换方式受限

**现状**：
- 减一线分流是**互斥型**（1:0 或 0:1），通过阀门物理切换
- 一个月只允许**一次切换**，且只能在**批次边界**切换
- [switch_planner.py:389](file:///d:/coding/huilian_tag_meixiao/solve_v1/backend/scheduling/switch_planner.py#L389) 硬编码"一个月只能切换一次阀门"

**不适用**：
- 批次内切换（第 5 天切，而非批次结束后切）
- 多次切换（第 5 天切、第 15 天切回、第 25 天再切）
- 切换点不是"选一个组合"，而是"随时间轴动态变化"

**影响**：Agent 无法实现精细化的切换策略优化。

#### 短板 2：只有减一线一个分流变量

**现状**：
- `special_vars` dict 只有 `jian1_to_diesel` 和 `jian1_to_wax` 两个 key
- [direct_calculator.py:45-59](file:///d:/coding/huilian_tag_meixiao/solve_v1/backend/calculation/direct_calculator.py#L45) `_init_special_vars` 只处理减一线
- 其他分流点（减渣、直柴等）的 `split_ratio` 从 DB 固定加载，不可在求解时调整

**不适用**：
- 减压渣油多少给溶脱、多少给 HC（需要动态调整比例）
- 直馏柴油多少给 1 加裂、多少给 2 加裂
- 任何 DB 中 `split_ratio` 固定但实际需要优化分配的场景

**影响**：多分流点联合优化无法实现，Agent 只能调减一线一个变量。

#### 短板 3：进料配比固定

**现状**：
- [refinery.py:352-361](file:///d:/coding/huilian_tag_meixiao/solve_v1/backend/models/refinery.py#L352) `get_feed_ratio` 从 DB `products` 表查固定 `yield_rate`
- [direct_calculator.py:145](file:///d:/coding/huilian_tag_meixiao/solve_v1/backend/calculation/direct_calculator.py#L145) `main_feed_totals[device_id] = device_input * feed_ratio`
- 配比不随上游分流变化而动态推导

**不适用**：
- 上游分流比例变化导致下游装置进料组成变化
- 混炼场景下多原油品种的进料配比需要动态计算
- 任何需要"物料流向一步步求解收率及输出量"的场景

**影响**：分流变化无法传播到下游，计算结果偏离实际。

#### 短板 4：负荷假设过于简化

**现状**：
- [batch_builder.py:79-145](file:///d:/coding/huilian_tag_meixiao/solve_v1/backend/calculation/batch_builder.py#L79) 月平均日处理量 = 月总量 / 月天数（均匀取料）
- [batch_builder.py:120](file:///d:/coding/huilian_tag_meixiao/solve_v1/backend/calculation/batch_builder.py#L120) `Σ(processing_days) = 月总天数`（全月持续加工）
- [batch_builder.py:193-196](file:///d:/coding/huilian_tag_meixiao/solve_v1/backend/calculation/batch_builder.py#L193) 停工期 CDU 仍全量产出（分子不减停工）
- 负荷校验用月度平均值，不反映阶段性峰值

**不适用**：
- 阶段性负荷调整（前 10 天 90%、中间 5 天 105%、后 15 天 95%）
- 高峰期装置超负荷但月均不超的场景
- 停工后恢复期的渐进式提负荷

**影响**：负荷校验不精确，可能误判可行性。

## 三、分流控制模式分类

### 3.1 两个维度的交叉

分流控制的复杂度来自**空间维度**和**时间维度**的交叉：

```
空间维度（怎么分）:
  ├── 互斥型 — 阀门物理限制，1:0 或 0:1（如减一线）
  └── 比例型 — 可按任意比例分流（如减渣、直柴）

时间维度（怎么变）:
  ├── 全程固定 — 整月不变
  ├── 一次切换 — 某天切换到另一种模式/比例
  └── 多次调整 — 多个时间点逐步调整
```

### 3.2 六种分流模式

| 模式 | 空间 | 时间 | 举例 | 当前引擎支持 |
|------|------|------|------|-------------|
| M1 | 互斥 | 全程固定 | 减一线整月去蜡油 | ✅ |
| M2 | 互斥 | 一次切换 | 减一线第12天从蜡油切到柴油 | ✅（仅批次边界） |
| M3 | 互斥 | 多次切换 | 减一线第5天切、第15天切回、第25天再切 | ❌ |
| M4 | 比例 | 全程固定 | 减渣整月 4:6 分流 | ❌ |
| M5 | 比例 | 一次调整 | 减渣前10天 4:6，后20天 3:7 | ❌ |
| M6 | 比例 | 多次调整 | 减渣第5天调、第15天再调 | ❌ |

### 3.3 复杂度的真正来源

复杂度不在于"加几个比例参数"，而在于**多分流点事件叠加 + 时间轴区间划分 + 全链路联动**：

#### 事件叠加

一个炼厂可能有 5~10 个分流点，每个都可能独立切换/调整，事件时间点不一定对齐：

```
减一线: 第5天切换, 第15天切回
减渣:   第10天调比例
直柴:   第8天调比例, 第20天调回
FCC负荷: 第1-10天 90%, 第11-20天 100%, 第21-30天 95%
```

合并后时间轴被切成 7 个区间。如果有 10 个分流点各自独立调整，最坏情况月度被切成几十个区间。

#### 全链路联动

改任何一个分流比例 → 下游装置进料组成变化 → 进料配比变化 → 收率变化 → 产出变化 → 负荷变化 → 罐容变化。这是一个全链路联动的过程：

```
分流比例变化
  → connection_flows 变化（流量）
    → total_feeds 变化（装置进料）
      → feed_ratio 变化（配比，当前固定）
        → yield_rate 变化（收率，当前固定）
          → device_output 变化（产出）
            → device_utilization 变化（负荷）
              → tank_level 变化（罐容）
```

当前引擎在第 3 步（配比）和第 4 步（收率）断了链——用固定值替代了动态推导，导致后续计算结果偏离实际。

#### 罐容动态平衡

不同区间的产出不同，中间罐的液位是随时间累积/消耗的：

```
第1-5天: 减一线→蜡油, 蜡油罐每天 +800吨, 柴油罐每天 0
第5天切换后: 减一线→柴油, 蜡油罐每天 0, 柴油罐每天 +800吨
```

罐容校验不能只看月度总量，要看**峰值液位**——某个时间段罐可能快满了，即使月度总量没超。

## 四、目标架构：区间级计算模型

### 4.1 计算模型升级

```
当前模型: 批次级计算
  批次 → 全批次统一分流 → 算一次 → 月度汇总
  时间复杂度: O(批次数)

目标模型: 区间级计算（事件驱动）
  事件合并 → 时间区间划分 → 逐区间算物理 → 罐容动态平衡 → 月度汇总
  时间复杂度: O(区间数 × 装置数)
  区间数 = 各分流点事件数的笛卡尔积（最坏情况）
```

### 4.2 计算流程

```
输入:
  - 排产计划（原油品种 + 加工量 + 时间分配）
  - 分流方案表（每个分流点的时间轴方案）
  - 负荷调度表（每个装置的时间轴负荷）
  - 停工声明

Step 1: 事件合并
  收集所有分流点和负荷调度的事件时间点
  合并为统一的时间轴区间
  例如: 30天的月 → [1-4, 5, 6-9, 10, 11-14, 15-19, 20-30] = 7个区间

Step 2: 逐区间物理计算
  对每个区间:
    - 确定本区间各分流点的模式/比例
    - 确定本区间各装置的负荷率
    - BFS 遍历计算流量、收率、产出
    - 记录本区间各罐的流入/流出

Step 3: 罐容动态平衡
  按时间轴逐区间累积:
    罐液位 += 本区间流入 - 本区间流出
    检查峰值液位是否超容

Step 4: 月度汇总
  合并各区间的装置负荷、产出、罐容
  生成 combination_metrics 摘要
```

#### `interval_calculator.py`（新引擎核心）

```python
def calculate_interval_physical(
    scenario_id: str,
    input_amount: float,
    interval: dict,                    # 区间定义 {start_day, end_day, days}
    split_decisions: dict,             # 本区间的分流方案
    load_schedule: dict,               # 本区间的负荷调度
    shutdown_intervals: dict = None,
    feed_ratios: dict = None,
) -> dict:
    """
    单区间物理计算。复用 direct_calculator 的 BFS 遍历和流量传播逻辑，
    但分流变量从 1 组变成 N 组，配比从固定查表变成动态推导。
    """
    # 1. 初始化 N 个分流点的 special_vars
    special_vars = _init_all_split_vars(split_decisions, scenario)

    # 2. BFS 拓扑遍历（复用现有逻辑）
    topology = _build_topology(scenario)

    # 3. 正向遍历算流量（改造：支持 N 个分流点 + 动态配比）
    device_inputs, connection_flows = _forward_traverse(
        topology, input_amount, special_vars, scenario,
        feed_ratios, load_schedule
    )

    # 4. 构建利用率（改造：按本区间负荷率计算）
    device_utilization = _build_interval_utilization(
        device_inputs, scenario, interval, load_schedule
    )

    return {
        'interval': interval,
        'device_inputs': device_inputs,
        'connection_flows': connection_flows,
        'device_utilization': device_utilization,
        'special_vars': special_vars,
        'tank_flows': _extract_tank_flows(connection_flows),
    }
```

#### `split_scheduler.py`（事件合并）

```python
def merge_events(split_decisions: dict, load_schedule: dict,
                 batch_timeline: list) -> list:
    """
    将所有分流点和负荷调度的事件时间点合并为统一的时间轴区间。

    输入: 各分流点的方案 + 负荷调度 + 批次时间线
    输出: 区间列表 [{start_day, end_day, days, split_state, load_state}]
    """
    # 1. 收集所有事件时间点
    event_days = set()
    event_days.add(1)  # 月初
    for split_point, schedule in split_decisions.items():
        for segment in schedule:
            event_days.add(segment['day_range'][0])
    for device, schedule in load_schedule.items():
        for segment in schedule:
            event_days.add(segment['day_range'][0])

    # 2. 排序，生成区间
    sorted_days = sorted(event_days)
    intervals = []
    for i in range(len(sorted_days)):
        start = sorted_days[i]
        end = sorted_days[i + 1] - 1 if i + 1 < len(sorted_days) else total_days
        intervals.append({
            'start_day': start,
            'end_day': end,
            'days': end - start + 1,
            'split_state': _resolve_split_state(split_decisions, start),
            'load_state': _resolve_load_state(load_schedule, start),
        })
    return intervals
```

#### `tank_balance.py`（罐容动态平衡）

```python
def calculate_tank_balance(
    interval_results: list,    # 各区间的计算结果
    tanks: dict,               # 罐容参数
) -> dict:
    """
    逐区间累积罐液位，检查峰值。

    返回: {
        'max_levels': {tank_id: max_level},        # 各罐峰值液位
        'overflow_tanks': [tank_id],               # 超容罐列表
        'timeline': [{day, tank_id, level}],       # 液位时间线
    }
    """
    current_levels = {tank_id: 0 for tank_id in tanks}
    max_levels = {tank_id: 0 for tank_id in tanks}
    timeline = []

    for result in interval_results:
        for tank_id, flow in result['tank_flows'].items():
            current_levels[tank_id] += flow['inflow'] - flow['outflow']
            max_levels[tank_id] = max(max_levels[tank_id], current_levels[tank_id])
            timeline.append({
                'day': result['interval']['end_day'],
                'tank_id': tank_id,
                'level': current_levels[tank_id],
            })

    overflow = [tid for tid, lvl in max_levels.items()
                if lvl > tanks[tid].capacity]
    return {'max_levels': max_levels, 'overflow_tanks': overflow, 'timeline': timeline}
```

#### `yield_resolver.py`（改造）

```python
def resolve_yield(scenario, device_id, product_id, crude_type, split_ratio=None):
    """
    改造：支持比例分流时的收率加权。

    当下游进料来自多个分流点时，收率不再是简单的二选一，
    而是按进料比例加权。
    """
    if split_ratio is None:
        # 互斥型：沿用现有逻辑
        return _resolve_xy_mode(scenario, device_id, product_id, crude_type)
    else:
        # 比例型：按进料组成加权
        weighted_yield = 0
        for source, ratio in split_ratio.items():
            yield_rate = _lookup_yield(scenario, device_id, product_id, source)
            weighted_yield += yield_rate * ratio
        return weighted_yield
```

## 六、演进路径

### 6.1 分阶段演进

```
阶段 0（当前）: 单变量批次级引擎
  ├── 1 个分流变量（减一线互斥）
  ├── 批次边界切换
  ├── 固定配比 + 固定收率
  └── 月均负荷

         ↓ 演进

阶段 1: 参数化 + 摘要返回（Agent 基础能力）
  ├── 规则参数化（feasibility_rules）         ← 已完成
  ├── 选优参数化（selection_strategy）        ← 已完成
  ├── MCP-01 返回 combination_metrics 摘要    ← 待实施
  └── mode 参数（reassess_only）              ← 待实施

         ↓ 演进

阶段 2: 通用分流 + 批次内切换
  ├── special_vars 从 1 组变成 N 组           ← 新建 interval_calculator
  ├── 支持比例型分流（M4 模式）               ← split_scheduler
  ├── 支持批次内切换（M3 模式）               ← interval_calculator
  ├── 进料配比动态推导                        ← 改造 _forward_traverse
  └── 收率按分流比例加权                      ← 改造 yield_resolver

         ↓ 演进

阶段 3: 区间级计算 + 罐容动态平衡
  ├── 事件合并 + 时间区间划分                 ← split_scheduler
  ├── 逐区间物理计算                          ← interval_calculator
  ├── 罐容动态平衡（峰值校验）                ← tank_balance
  └── 阶段性负荷调度                          ← load_schedule 参数

         ↓ 演进

阶段 4: 优化 + 缓存
  ├── 区间复用缓存（相同区间不重算）
  ├── 增量计算（只算变化的区间）
  └── Agent 闭环迭代验证
```

### 6.2 各阶段改造量

| 阶段 | 新建文件 | 改造文件 | 工作量 | 风险 |
|------|---------|---------|--------|------|
| 阶段 1 | 0 | 2 | 小 | 低 |
| 阶段 2 | 2 | 3 | 大 | 高（影响计算结果） |
| 阶段 3 | 2 | 1 | 大 | 高（新计算模型） |
| 阶段 4 | 0 | 2 | 中 | 低 |

## 七、演进难度分析

### 7.1 技术难度

| 难点 | 难度 | 原因 |
|------|------|------|
| 区间级计算模型 | ⭐⭐⭐⭐ | 从"算一次"变成"算 N 次再汇总"，计算逻辑复杂度质变 |
| 多分流点联动 | ⭐⭐⭐⭐ | 改一个分流点影响全链路，需要确保传播正确 |
| 收率加权 | ⭐⭐⭐ | 比例分流时收率不是简单查表，需要按进料组成加权 |
| 罐容动态平衡 | ⭐⭐⭐ | 从月度总量校验改为逐区间累积，需要跟踪液位时间线 |
| 事件合并 | ⭐⭐ | 逻辑清晰，但边界条件多（空方案、单事件、对齐事件） |
| 向后兼容 | ⭐⭐⭐ | 不传决策方案时回退到旧逻辑，需要双引擎并存 |

### 7.2 复杂度控制手段

| 手段 | 效果 | 适用阶段 |
|------|------|---------|
| 限制事件数 | 每个分流点每月最多 2~3 次调整 → 区间数可控（10~20 个） | 阶段 3 |
| 区间复用 | 相邻区间如果分流和负荷相同则合并 → 减少实际计算次数 | 阶段 4 |
| 增量计算 | 只重算变化的区间，不变的不重算 | 阶段 4 |
| Agent 控制粒度 | Agent 给"前10天/中5天/后15天"粗粒度，不需要精确到每天 | 全阶段 |
| 双引擎并存 | 旧引擎处理简单场景，新引擎处理复杂场景 | 阶段 2~3 |

### 7.3 性能影响

```
当前引擎: 8~16 个组合 × 1 次计算 = 8~16 次物理计算
阶段 3:   8~16 个组合 × 7~15 个区间 × 1 次计算 = 56~240 次物理计算
阶段 4:   8~16 个组合 × 3~5 个有效区间（复用后） = 24~80 次物理计算
```

阶段 3 性能下降约 10 倍，阶段 4 通过缓存可控制在 3~5 倍。对于分钟级求解场景，可接受。

## 八、注意点

### 8.1 向后兼容

- 不传 `split_decisions` 和 `load_schedule` 时，回退到旧引擎（`direct_calculator`）
- 新旧引擎双引擎并存，通过 `mode` 参数切换
- 旧 API、旧前端不改动，新能力通过新参数启用
- DB schema 扩展用 `IF NOT EXISTS`，兼容旧数据

### 8.2 计算结果一致性

- 阶段 1（参数化）不改变计算结果，只改变判定/选优逻辑
- 阶段 2~3（新引擎）会改变计算结果——因为配比和收率从固定变成动态
- 需要建立**回归测试基线**：用旧引擎跑一批结果，新引擎跑相同参数（不传决策方案），对比结果一致性
- 新引擎传默认决策方案（减一线互斥、配比查表）时，结果应与旧引擎一致

### 8.3 数据一致性

- 分流方案是"计算输入"，不应持久化到 DB（除非用户明确 save_data）
- 负荷调度是"计算输入"，同上
- DB 中的 `split_ratio` 仍是默认值，Agent 传入的 `split_decisions` 是运行时覆盖

### 8.4 Agent 交互设计

- Agent 不需要理解区间划分的细节——Agent 只给分流方案和负荷调度，引擎内部合并区间
- `combination_metrics` 摘要需要包含区间信息（如"峰值负荷出现在第 12 天"），供 Agent 评估
- Skill 需要补充分流点清单和调优指导

### 8.5 逐步验证

- 阶段 1 完成后：验证 Agent 闭环迭代（探索→评估→调优→再求解）
- 阶段 2 完成后：验证单分流点比例分流的正确性（对比手工计算）
- 阶段 3 完成后：验证多分流点联动的全链路传播正确性
- 每个阶段都需要回归测试，确保不破坏已有功能

## 九、与 Agent 架构的衔接

### 9.1 引擎能力与 Agent 定制层次的关系

| Agent 定制层 | 需要的引擎能力 | 对应演进阶段 |
|-------------|--------------|------------|
| L1 参数级（调阈值/策略） | 规则参数化 | 阶段 1（已完成规则部分） |
| L2 模式级（选管线分支） | mode 参数 | 阶段 1（待实施） |
| L3 编排级（自定义切换方案） | switch_plan + 批次内切换 | 阶段 2 |
| L4 全定制（多分流点 + 阶段负荷） | 区间级计算模型 | 阶段 3 |

### 9.2 Agent 闭环示例（阶段 3 完成后）

```
用户："减一线前5天去蜡油、后25天去柴油；减渣4:6分流；
       FCC前10天90%负荷后20天满负荷；液化气不超500"

Agent:
  1. 组装 split_decisions + load_schedule（Skill 指导）
  2. solve_refinery_plan(
       mode="full",
       switch_mode="custom",
       split_decisions={
         "jian1": [{"day_range": [1,5], "mode": "WAX"},
                   {"day_range": [6,30], "mode": "DIESEL"}],
         "vacuum_residue": [{"day_range": [1,30],
           "ratio": {"to_sda": 0.4, "to_hc": 0.6}}]
       },
       load_schedule={
         "FCC": [{"day_range": [1,10], "load_rate": 0.90},
                 {"day_range": [11,30], "load_rate": 1.00}]
       },
       feasibility_rules={"max_load_rate": 100.0}
     )
  3. 引擎内部: 事件合并 → 区间划分 → 逐区间计算 → 罐容平衡 → 汇总
  4. 返回 combination_metrics（含峰值负荷、峰值罐位、液化气产出等）
  5. Agent 评估: lpg=480 ✓, FCC峰值=100% ✓, 罐容未超 ✓
  6. 推荐
```

### 9.3 引擎定型标准

引擎完成阶段 3 后即定型，后续所有新约束由 Agent 在摘要上自评估：

- ✅ 支持任意分流点的互斥/比例分流
- ✅ 支持任意时间点的切换/调整
- ✅ 支持阶段性负荷调度
- ✅ 返回轻量摘要供 Agent 自评估
- ✅ 罐容动态平衡（峰值校验）

后续不需要为每种新约束改引擎，只需要：
1. 给 `combination_metrics` 加字段（如果摘要缺少某个指标）
2. 给 Skill 补充领域知识（如果新增一类约束场景）

## 十、总结

### 10.1 核心判断

当前引擎的骨架（BFS 拓扑遍历、正向流量传播、停工折减）是合理的，不需要推翻重来。需要的是**计算模型的升级**——从"单变量批次级"到"多变量区间级"。

### 10.2 演进的本质

```
当前: 1 个决策变量 × 批次级计算 = 简单但不可定制
目标: N 个决策变量 × 区间级计算 = 复杂但完全可定制
```

这不是加几个参数能解决的，是计算模型的质变。但通过分阶段演进（阶段 1→4），可以控制风险和复杂度。

### 10.3 关键决策点

| 决策 | 建议 | 理由 |
|------|------|------|
| 是否新建引擎 | ✅ 新建 `interval_calculator` | 与旧引擎并存，不破坏现有功能 |
| 是否改 DB schema | ✅ 加列扩展 | 兼容旧数据 |
| 是否一次性完成 | ❌ 分 4 阶段 | 控制风险，逐步验证 |
| 阶段 1 是否独立可用 | ✅ 不依赖阶段 2~3 | 参数化 + 摘要返回已能覆盖 90% 定制场景 |
| 阶段 2~3 是否必须 | ⚠️ 看业务需求 | 如果只需要 L1~L2 定制，阶段 1 足够 |
