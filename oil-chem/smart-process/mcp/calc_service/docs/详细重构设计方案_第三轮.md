# 详细重构设计方案 — 第三轮（MCP 封装就绪）

> **版本**: v1.0 · 2026-08
> **基准代码**: 第二轮重构后（calc_ctx 已消除，纯函数计算层）
> **设计目标**: 消除计算层签名中的非 JSON 可序列化参数，使 14 个 MCP 候选函数全部达到"MCP 可直接封装"标准

---

## 一、问题分析

### 1.1 MCP 封装的核心原则

一个函数能被 MCP 直接封装，当且仅当：

```
MCP 输入 (JSON) → 适配层加载 domain 对象 → 函数(domain 对象) → 适配层序列化 → MCP 输出 (JSON)
```

**适配层可以处理的**（不算阻塞）:
- `RefineryScenario` 对象 — 适配层从 `scenario_id` 加载，传入函数
- `prices: Dict[str, float]` — 适配层从 DB 预加载，传入函数
- `CombinationResult` 对象 — 适配层从 JSON 反序列化

**适配层无法处理的**（真正的阻塞）:
- `load_scenario_fn: Callable` — Python 闭包，无法从 JSON 构造
- `scenario_cache: Dict` — 可变状态，按引用传递，跨调用累积
- `repo: RefineryRepository` — DB 连接对象，calculation 层不应出现
- `econ_cache: Dict` — 跨组合优化缓存，属于内部实现细节

### 1.2 阻塞点清单

| # | 阻塞模式 | 出现位置 | 出现次数 | 严重度 |
|---|---------|---------|---------|--------|
| 1 | `load_scenario_fn: Callable` | 5 个计算层函数签名 | 5 | **高** — 无法 JSON 序列化 |
| 2 | `scenario_cache: Dict` (可变引用) | 4 个计算层函数签名 | 4 | **高** — 跨调用状态泄漏 |
| 3 | `physical_cache: dict` | `evaluate_combination` 签名 | 1 | **中** — 内部优化暴露 |
| 4 | `hangmei_precompute_cache: dict` | `evaluate_combination` + `_precompute_hangmei_batch_data` | 2 | **中** — 内部优化暴露 |
| 5 | `econ_cache: Dict` | `recompute_combination_economics` 签名 | 1 | **中** — 内部优化暴露 |
| 6 | `repo` (RefineryRepository) | `build_jian1_switch_analysis` 签名 | 1 | **低** — 死代码，函数体内未使用 |
| 7 | `Callable` import | 3 个计算层文件 | 3 | **低** — 随 #1 消除而清除 |

### 1.3 受影响函数清单

```
combination_evaluator.py:
  _precompute_hangmei_batch_data  ← 阻塞 #1 #2 #4
  evaluate_combination            ← 阻塞 #1 #2 #3 #4
  recompute_combination_economics ← 阻塞 #1 #2 #5

combination_optimizer.py:
  optimize_combinations           ← 阻塞 #1 (创建 scenario_cache 内部变量)

hangmei_optimizer.py:
  build_hangmei_context           ← 阻塞 #1

switch_analysis.py:
  build_jian1_switch_analysis     ← 阻塞 #6 (死参数)

solve_service.py:
  _evaluate_and_pick              ← 传递 load_scenario_fn
  _eval_all_combos_final          ← 传递 scenario_cache + load_scenario_fn
  _annotate_combo_capacity        ← 传递 load_scenario_fn
  comprehensive_solve             ← 传递 load_scenario_fn 给 build_hangmei_context
```

## 二、重构方案总览

### 2.1 核心思路

```
重构前:
  evaluate_combination(combo, batches, scenario_cache, custom_crude_costs,
                       load_scenario_fn, ..., physical_cache, hangmei_precompute_cache, ...)
                       ↑ 可变状态        ↑ 闭包                ↑ 内部缓存        ↑ 内部缓存

重构后:
  evaluate_combination(combo, batches, scenarios, custom_crude_costs,
                       ..., prices, device_costs, feed_ratios)
                       ↑ 预加载只读 dict
```

**关键变化**:
1. `load_scenario_fn` + `scenario_cache` → `scenarios: Dict[str, RefineryScenario]`（预加载只读字典）
2. `physical_cache` / `hangmei_precompute_cache` / `econ_cache` → 移入 `optimize_combinations` 内部管理
3. `repo` 死参数 → 直接删除

### 2.2 Phase 划划

| Phase | 目标 | 影响函数数 | 优先级 |
|-------|------|-----------|--------|
| Phase 1 | 消除 `load_scenario_fn` + `scenario_cache` → `scenarios: Dict` | 5 计算 + 4 服务 | **高** |
| Phase 2 | 内化 `physical_cache` / `hangmei_precompute_cache` / `econ_cache` | 2 计算 + 1 服务 | **高** |
| Phase 3 | 删除 `build_jian1_switch_analysis` 死参数 `repo` | 1 计算 + 1 服务 | **低** |
| Phase 4 | 提取 `SolveService` 纯编排函数 | 2 服务方法 | **中** |
| Phase 5 | 清理 `Callable` import + `scenario_cache` 返回值 | 3 计算 + 1 服务 | **低** |

**执行顺序**: Phase 1 → Phase 2 → Phase 3 → Phase 5 → Phase 4

## 三、Phase 1: 消除 `load_scenario_fn` + `scenario_cache`

### 3.1 设计思路

将"惰性加载"（调用时按需 `load_scenario_fn`）改为"预加载"（调用前一次性加载所有场景，传入只读 dict）。

```
重构前（惰性加载）:
  Service 层
    │ 传入 load_scenario_fn + 空 scenario_cache
    ▼
  optimize_combinations
    │ 创建 scenario_cache = {}
    │ 传入 load_scenario_fn + scenario_cache
    ▼
  evaluate_combination
    │ if crude_type not in scenario_cache:
    │   scenario_cache[crude_type] = load_scenario_fn(...)
    │ scenario = scenario_cache[crude_type]
    ▼
  calculate_direct(scenario, ...)

重构后（预加载）:
  Service 层
    │ scenarios = {crude_type: load_scenario(crude_type) for ...}  # 预加载
    │ 传入 scenarios（只读 dict）
    ▼
  optimize_combinations
    │ 传入 scenarios
    ▼
  evaluate_combination
    │ scenario = scenarios[crude_type]  # 直接取，无惰性加载
    ▼
  calculate_direct(scenario, ...)
```

## 四、Phase 2: 内化优化缓存

### 4.1 设计思路

`physical_cache`、`hangmei_precompute_cache`、`econ_cache` 是跨组合优化缓存，只在 `optimize_combinations` / `_eval_all_combos_final` 的批量循环中有意义。当 `evaluate_combination` / `recompute_combination_economics` 被 MCP 单独调用时，这些缓存应该不存在。

**方案**: 将缓存参数移到函数签名的末尾，标注为内部优化参数。MCP 适配层不传这些参数（使用默认 None），`optimize_combinations` 内部创建并传入。

### 4.2 缓存归属

| 缓存 | 创建者 | 使用者 | MCP 单独调用时 |
|------|--------|--------|---------------|
| `physical_cache` | `optimize_combinations` | `evaluate_combination` | None（每次重算） |
| `hangmei_precompute_cache` | `optimize_combinations` | `evaluate_combination` → `_precompute_hangmei_batch_data` | None（每次重算） |
| `econ_cache` | `_eval_all_combos_final` | `recompute_combination_economics` | None（每次重算） |

### 4.3 变更内容

**`evaluate_combination`**: `physical_cache` / `hangmei_precompute_cache` 保留为可选参数（默认 None），但在 docstring 中标注:

```python

    combo: dict, batches: List[dict],
    scenarios: Dict[str, RefineryScenario],

    hangmei_ctx: Optional[HangmeiContext] = None,
    plan_month: str = None,
    logger=None,
    capacity_only: bool = False,
    summary_only: bool = False,
    prices: Optional[Dict[str, float]] = None,
    device_costs: Optional[Dict[int, float]] = None,
    feed_ratios: Optional[Dict[str, Dict[str, float]]] = None,
    # ── 以下为内部优化参数，MCP 封装时不传 ──
    _physical_cache: dict = None,
    _hangmei_precompute_cache: dict = None,

```

**注意**: 参数名加 `_` 前缀，表示内部使用。MCP 适配层不会传这些参数。

## 六、Phase 4: 提取 `SolveService` 纯编排函数

### 6.1 问题

`comprehensive_solve` 和 `optimize_valve` 是 `SolveService` 的实例方法，内部混合了三类逻辑:
1. DB 访问（创建 repo、加载计划、保存结果）
2. 纯编排（批次划分→组合枚举→评估→选优）
3. 结果组装（聚合经济、生成说明、构建流程图）

MCP 适配层需要能复用第 2、3 类逻辑，而不依赖 `SolveService` 实例。

### 6.3 `SolveService` 变为薄入口

```python
class SolveService:
    def comprehensive_solve(self, plan_month, production_plans_input, ...):
        """DB 入口：加载数据 → 调用纯编排 → 保存结果。"""
        # 1. DB: 加载计划
        repo = self._sched_repo()
        plan = self._produce_plan(repo, ...)
        switches = self._enumerate_switches(plan.details, ...)
        tank_initials = self._load_tank_initials(plan_month)

        # 2. 预加载引用数据
        scenarios, prices_prev, device_costs_prev, feed_ratios_prev = \
            self._preload_reference_data(switches.batches, prev_month, ...)
        prices_final, device_costs_final, feed_ratios_final = \
            self._preload_prices_only(switches.batches, plan_month, ...)

        # 3. 纯编排
        result = run_comprehensive_solve(
            plan_details=plan.details,
            custom_crude_costs=plan.custom_crude_costs,
            batches=switches.batches,
            combinations=switches.combinations,
            scenarios=scenarios,
            prices_prev=prices_prev,
            device_costs_prev=device_costs_prev,
            feed_ratios_prev=feed_ratios_prev,
            prices_final=prices_final,
            device_costs_final=device_costs_final,
            feed_ratios_final=feed_ratios_final,
            hangmei_target=hangmei_target,
            select_month=prev_month,
            final_month=plan_month,
            tank_initials=tank_initials,
            logger=self.logger)

        # 4. DB: 保存结果
        self._update_device_load_rate(result['batch_details'], ..., repo)
        return result
```

## 十二、`RefineryScenario` 入参语义分析与场景依赖声明

### 12.1 问题

`RefineryScenario` 包含 14+ 个顶层字段（devices、products、material_flows、connections、start_device_id、cdu_device_id、crude_type、processing_device_ids、yield_switch_device_ids、hangmei_active_device_ids、tank_device_ids、intermediate_tank_ids、material_name_map、product_material_map...），但不同函数实际使用的字段数从 0 到 11+ 不等。这会导致：

- **入参语义模糊**: Agent 看到 `scenario_id` 不知道它隐含哪些数据依赖
- **测试构造冗余**: 测试 `compute_revenue`（只用 4 个字段）需要构造完整 scenario（14+ 字段）
- **输入校验盲区**: 适配层无法校验"scenario 是否包含函数所需字段"

### 12.3 设计决策：不拆分，补充场景依赖声明

**不拆分 `RefineryScenario` 的理由**:

1. **参数爆炸**: `_forward_traverse` 需要拆成 11+ 个参数，比 scenario 更难理解
2. **一致性丧失**: 有些函数接收 scenario，有些接收散装 dict，调用方需要记住每个函数的"口味"
3. **关系完整性丧失**: `connections` 从 `material_flows` 派生，`cdu_device_id` 从 `devices` 推断——拆开后这些派生关系需要在调用方手动维护
4. **MCP 非阻塞**: 适配层从 `scenario_id` 加载完整 scenario 传入即可，不需要知道函数用了哪些字段

**方案**: 为每个接收 scenario 的 MCP 候选函数在 docstring 中添加**场景依赖声明**，让 Agent 和适配层都能明确函数对 scenario 的数据依赖。
