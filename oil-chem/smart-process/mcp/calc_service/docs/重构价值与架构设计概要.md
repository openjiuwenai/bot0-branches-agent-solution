# 求解器重构价值与架构设计概要

> 文档版本：v1.0  
> 日期：2026-08-04  
> 范围：solve_v1/backend 效益求解器

---

## 一、当前现状

### 1.1 系统概况

求解器核心入口 `comprehensive_solve` 位于 `service/solve_service.py`，执行 3 趟评估（PASS 1 选优 / PASS 3 最终核算 / PASS 4 全组合本月价评估），涉及约 20 个核心函数、8 层调用深度，典型求解耗时 1.5 秒。

### 1.2 调用链全景

```
comprehensive_solve (1层)
  ├─ _produce_plan → 排产计划加载
  ├─ _enumerate_switches → 批次枚举 + 切换组合
  ├─ _evaluate_and_pick (2层)
  │    └─ optimize_combinations (3层)
  │         ├─ _preload_all_prices → 价格预加载
  │         └─ for combo: evaluate_combination (4层)
  │              ├─ calculate_direct (5层)
  │              │    ├─ calculate_physical (6层) → resolve_yield_rate (7层)
  │              │    └─ generate_explanation (6层)
  │              │         ├─ compute_revenue (7层) → get_product_price (8层)
  │              │         └─ compute_costs (7层)
  │              ├─ _build_batch_details_list
  │              ├─ _build_monthly_load
  │              └─ TankCapacityChecker.check
  ├─ _enrich_combo_batch_details → 可行性重定 + 重选最优
  ├─ [PASS 3] evaluate_combination(summary_only=False)
  └─ [PASS 4] _eval_all_combos_final
       └─ for combo: recompute_combination_economics
```

### 1.3 性能优化机制

当前系统通过 6 层内存缓存实现性能优化：

| 缓存层 | 位置 | Key | 作用 | 性能影响 |
|--------|------|-----|------|---------|
| scenario_cache | batch_optimizer 局部变量 | crude_type | 跨 PASS 共享场景（含价格） | 58 次 DB→1 次批量加载 |
| physical_cache | batch_optimizer 局部变量 | (batch_id, mode, hangmei_window) | 跨组合共享物理计算 | 2n²→3n（省 85%） |
| hangmei_precompute_cache | batch_optimizer 局部变量 | (batch_id, mode) | 跨组合共享航煤预计算 | 2n×D→2×D（省 80%） |
| econ_cache | solve_service 局部变量 | (batch_id, mode, hangmei_params) | PASS 4 跨组合共享经济结果 | 4n²→4n（省 80%） |
| scenario 惰性缓存 | scenario 对象属性 | — | 拓扑/价格表/CDU 分类 | 避免重复构建 |
| pass1_results | SolutionStage | combination_id | PASS 1→PASS 4 物理结果复用 | 零冗余 |

### 1.4 数据流

一次完整求解（n 批次 × m 组合）的数据流：
- PASS 1：m × n 个 calc_result，存入 pass1_results（m 个 CombinationResult）
- PASS 3：1 × n 个 calc_result（全量重算最优组合）
- PASS 4：m × n 个 explanation 重算（复用物理结果）
- CombinationResult：17 个字段，含 6 个跨 PASS 传递字段

## 二、问题诊断

### 2.1 Scenario 对象被"寄生"变异

**问题**：RefineryScenario 本应是只读的领域数据载体，却被 6 个计算文件写入了 10 个私有缓存属性。

| 写入位置 | 写入字段 | 用途 |
|---------|---------|------|
| direct_calculator.py:93 | `_device_order` | 装置拓扑序 |
| direct_calculator.py:120 | `_feed_ratio_cache` | 进料配比缓存 |
| direct_calculator.py:147 | `_main_feed_yr_cache` | 主进料收率缓存 |
| direct_calculator.py:158 | `_target_flow_map_cache` | 目标流量映射 |
| economics.py:109 | `_cdu_product_classification` | CDU 侧线分类 |
| economics.py:256 | `_price_table` | 按月分桶价格表 |
| revenue_calculator.py:77 | `_tank_mapping_cache` | 装置→罐映射 |
| revenue_calculator.py:96 | `_tank_flow_mapping_cache` | 罐流量映射 |
| revenue_calculator.py:124 | `_resolve_total_feed_cache` | 总进料缓存 |
| cost_calculator.py:101 | `_device_cost_cache` | 按月分桶装置成本 |

**后果**：
- scenario 无法序列化（含运行时缓存对象）
- scenario 无法跨进程传输（MCP 的基础障碍）
- `_price_table` 按月分桶设计本身就是变异副作用的补救——因为同一个 scenario 被两个月份的价格评估共用，不得不分桶隔离

### 2.2 函数签名不透明

15 个计算函数接收 scenario 参数，但每个实际只读其中一小部分：

| 函数 | 实际读取字段数 | 签名可见性 |
|------|--------------|-----------|
| get_product_price | 2 | 看不出只依赖 price_costs 和 _price_table |
| resolve_yield_rate | 2 | 看不出只依赖 yield_switch_ids 和 hangmei_active_ids |
| _find_start_device_input | 1 | 看不出只依赖 devices 的 type 字段 |
| calculate_physical | 16 | 看不出和 get_product_price 依赖差异巨大 |

**后果**：函数签名无法告诉你函数到底依赖什么，无法独立测试（必须构造完整 scenario）。

### 2.3 缓存传递不一致

四个缓存的传递方式五花八门：

| 缓存 | 传递方式 | 问题 |
|------|---------|------|
| physical_cache | 函数参数 | 可见但冗长 |
| hangmei_precompute_cache | 函数参数 | 同上 |
| econ_cache | 函数参数 | 同上 |
| scenario_cache | 参数→实例属性→参数（三段式） | 流转路径不可追踪 |

所有缓存均为**可变 dict 就地填充**，调用方读取的是被调用方填充后的副作用，数据流隐式双向。

### 2.4 层级反向依赖

文件头声明依赖方向：`service → calculation → data → models`，但实际：

```
batch_optimizer.py:1248  from ..service.solve_service import _build_batch_details_list
batch_optimizer.py:1339  from ..service.solve_service import merge_intervals
batch_optimizer.py:1821  from ..service.solve_service import _build_batch_details_list
```

calculation 层反向依赖 service 层，通过延迟 import 规避循环导入。**evaluate_combination 无法脱离 solve_service 独立运行**。

### 2.5 CombinationResult 是 God Object

17 个字段，角色混乱：

| 角色 | 字段数 | 典型字段 |
|------|--------|---------|
| 纯最终结果 | 8 | combination_id, total_revenue, switches |
| 纯中间传递 | 5 | calc_results, explanations, batch_details |
| 双重角色 | 4 | batch_results, hangmei_summary, feasible, monthly_load |

还有 4 个下划线临时键（`_calc_results`、`_explanations` 等）被塞进 dict 只是为了让 `_enrich` 再 pop 掉。

### 2.6 _enrich 的三重副作用

`_enrich_combo_batch_details` 一个函数同时做了：
1. 数据搬运（pop 4 个临时键）
2. 字段变换（set/覆盖 6 个字段）
3. 深层变异（修改嵌套 dict 内部值）
4. 业务决策（重定可行性 + 重选最优）

## 三、为什么重构

### 3.1 核心矛盾

当前求解器的性能优势来自 **6 层内存缓存 + 3 趟紧耦合评估**，这是对的。但缓存的**挂载位置和传递方式**不对——寄生在 scenario 对象上，通过可变 dict 隐式传递。

**一句话总结**：Scenario 是数据，不是上下文。缓存是上下文，不是数据。当前代码用一个对象同时承担了两个职责。

### 3.2 重构价值

#### 对 MCP 封装的益处

| 重构前 | 重构后 |
|--------|--------|
| 计算函数无法脱离 service 层独立调用（反向依赖） | 每个函数可独立暴露为 MCP Tool |
| scenario 无法序列化（含运行时缓存对象） | scenario 可 JSON 序列化，MCP 可传输 |
| 必须构造完整 scenario 才能测试 | 只需传几个 dict 就能测试和调用 |
| 缓存生命周期不可控 | CalcContext 显式创建、显式传递、显式销毁 |

重构后可封装的 MCP Tool：

| MCP Tool | 对应函数 | 依赖 |
|----------|---------|------|
| resolve_yield | resolve_yield_rate | yield_switch_ids, hangmei_active_ids |
| calculate_physical | calculate_physical | devices, connections, products, material_flows |
| check_tank_capacity | TankCapacityChecker.check | tank_ids, devices, material_flows |
| compute_economics | generate_explanation | products, price_table, devices |
| enumerate_switches | ValveSwitchPlanner | batches, shutdown_config |
| solve_comprehensive | comprehensive_solve | 全量（内部管理缓存） |

#### 对工程质量的益处

| 维度 | 改善 |
|------|------|
| 可测试性 | 计算函数可单元测试，无需 mock scenario |
| 可调试性 | 每个函数的输入输出明确，问题定位容易 |
| 可维护性 | 新增计算逻辑不影响其他模块 |
| 可序列化 | scenario 可序列化为 JSON，支持跨进程传输 |
| 层级正确 | 消除 calculation→service 反向依赖 |

### 3.3 什么不该改

以下设计是正确的工程优化，重构时必须保留：

| 设计 | 保留理由 |
|------|---------|
| 3 趟评估 | 双价格月是业务需求 |
| physical_cache 跨组合复用 | 2n²→3n，省 85% |
| scenario_cache 按 oil_type 缓存 | 避免 58 次 DB 查询 |
| 价格批量预加载 | 42 次 HTTP→1 次 |
| pass1_results 跨 PASS 复用 | 零冗余 |

**重构原则**：缓存机制不变，缓存的挂载位置和传递方式改变。

## 四、重构架构设计方案

### 4.1 目标架构

```
┌─────────────────────────────────────────────────────┐
│  Service 层（有状态，管生命周期）                      │
│                                                       │
│  · 创建 scenario_cache，管理其生命周期                │
│  · 创建 CalcContext（缓存容器），管理其生命周期        │
│  · 编排 3 趟评估，管理 PASS 间数据传递                │
│  · 调用 calculation 层的工具函数                      │
│                                                       │
│  comprehensive_solve                                  │
│    ├─ 创建 scenario_cache + calc_ctx                  │
│    ├─ PASS 1: for combo:                              │
│    │    physical = calculate_physical(                 │
│    │        devices, connections, products,            │
│    │        material_flows, calc_ctx)                  │
│    │    econ = generate_explanation(                   │
│    │        products, price_table, devices,            │
│    │        physical, calc_ctx)                        │
│    │    store in pass1_results[combo_id]               │
│    ├─ PASS 3: 重算最优组合                             │
│    └─ PASS 4: 复用 PASS 1 物理结果                     │
│                                                       │
├───────────────────────────────────────────────────────┤
│  Calculation 层（无状态，纯计算工具）                  │
│                                                       │
│  每个函数只接收自己需要的数据 + 可选的缓存参数：       │
│                                                       │
│  calculate_physical(devices, connections, ...)         │
│  generate_explanation(products, price_table, ...)      │
│  compute_revenue(products, price_table, devices, ...)  │
│  resolve_yield_rate(device_id, product, ...)           │
│  TankCapacityChecker.check(batches, tank_ids, ...)     │
│                                                       │
├───────────────────────────────────────────────────────┤
│  Data 层（只读，数据访问）                             │
│                                                       │
│  RefineryRepository.load_scenario() → RefineryScenario│
│  preload_prices(scenario, plan_month)                  │
│                                                       │
├───────────────────────────────────────────────────────┤
│  Models 层（纯数据结构）                               │
│                                                       │
│  RefineryScenario（纯域数据，只读）                    │
│  CalcContext（缓存容器，由 Service 层管理）            │
│  PhysicalResult / RevenueResult / CombinationOutput   │
└─────────────────────────────────────────────────────┘
```

### 4.2 核心设计：CalcContext

将所有计算缓存从 scenario 剥离到独立的 `CalcContext` 对象：

```python
@dataclass
class CalcContext:
    """计算缓存容器，由 Service 层创建和管理生命周期"""
    # 拓扑缓存
    device_order: Optional[List[str]] = None
    feed_ratio_cache: Dict = field(default_factory=dict)
    main_feed_yr_cache: Dict = field(default_factory=dict)
    target_flow_map_cache: Dict = field(default_factory=dict)

    # 经济缓存
    price_table: Dict[str, Dict[str, float]] = field(default_factory=dict)  # 按月分桶
    cdu_product_classification: Optional[dict] = None
    device_cost_cache: Dict[str, Dict[int, float]] = field(default_factory=dict)  # 按月分桶

    # 收入缓存
    tank_mapping_cache: Optional[Dict[str, str]] = None
    tank_flow_mapping_cache: Optional[Dict] = None
    resolve_total_feed_cache: Dict = field(default_factory=dict)
```

### 4.3 核心设计：Scenario 纯化

RefineryScenario 只保留域数据，移除所有 `_xxx_cache` 写入：

```python
@dataclass
class RefineryScenario:
    # 域数据（只读）
    crude_type: str
    crude_oil_price: float
    crude_costs: Dict[str, float]
    devices: Dict[str, Device]
    products: Dict[str, Product]
    material_flows: Dict[str, MaterialFlow]
    energy_consumptions: List[EnergyConsumption]
    price_costs: Dict[str, Dict[str, float]]  # 按月分桶

    # 模型派生数据（首次访问构建，只读）
    @property
    def connections(self) -> Dict[str, Connection]: ...
    @property
    def cdu_device_id(self) -> str: ...
    @property
    def processing_device_ids(self) -> Set[str]: ...
    # ... 其他派生属性

    # 移除：_device_order, _price_table, _tank_mapping_cache 等所有计算缓存
```

### 4.4 核心设计：函数签名透明化

计算函数从 `f(scenario, ...)` 改为 `f(具体数据, ...)`：

```python
# 重构前
def calculate_physical(scenario, input_amount, yield_mode, ...):
    devices = scenario.devices
    connections = scenario.connections
    products = scenario.products
    device_order = scenario._device_order  # 寄生缓存
    ...

# 重构后
def calculate_physical(
    devices: Dict[str, Device],
    connections: Dict[str, Connection],
    products: Dict[str, Product],
    material_flows: Dict[str, MaterialFlow],
    start_device_id: str,
    cdu_device_id: str,
    processing_device_ids: Set[str],
    yield_switch_device_ids: Set[str],
    hangmei_active_device_ids: Set[str],
    tank_device_ids: Set[str],
    input_amount: float,
    yield_mode: str,
    days: int = 1,
    calc_ctx: Optional[CalcContext] = None,  # 显式缓存参数
) -> PhysicalResult:
    ...
```

### 4.5 核心设计：CombinationResult 拆分

```python
# 中间态（PASS 间传递）
@dataclass
class PassResult:
    combination_id: str
    calc_results: List[dict]       # 物理结果
    explanations: List[dict]       # 经济结果
    batch_results: List[dict]      # 批次摘要
    hangmei_summary: dict
    batch_details: List[dict]
    monthly_load: dict

# 最终输出（对外）
@dataclass
class CombinationOutput:
    combination_id: str
    description: str
    switch_position: int
    initial_mode: str
    switches: Dict
    total_revenue: float
    total_cost: float
    feasible: bool
    near_feasible: bool
    infeasible_summary: str
    tank_check_result: dict
    batch_details: List[dict]
    monthly_load: dict
```

### 4.6 核心设计：消除反向依赖

将 `_build_batch_details_list` 和 `_build_monthly_load` 从 service 层下移到 calculation 层，消除 batch_optimizer → solve_service 的延迟 import。

### 4.7 MCP 封装架构（重构后）

```
┌──────────────────────────────────────────────┐
│              Agent (LLM)                      │
│  决策层：参数决策 + 结果解读 + what-if 分析   │
└──────┬───────────────────────┬───────────────┘
       │                       │
 ┌─────▼─────┐          ┌──────▼──────┐
 │  solve    │          │  primitive  │
 │  MCP      │          │  MCP (可选) │
 │           │          │             │
 │solve_     │          │resolve_yield│
 │comprehensive          │calc_physical│
 │(全量求解) │          │check_tank   │
 │           │          │compute_econ │
 └─────┬─────┘          └──────┬──────┘
       │                       │
 ┌─────▼───────────────────────▼──────┐
 │         data_service MCP (已有)     │
 │  list_units / list_tanks / get_prices│
 └─────────────────┬──────────────────┘
                   │
          ┌────────▼────────┐
          │   PostgreSQL     │
          └─────────────────┘
```

重构后计算函数可独立暴露为 MCP Tool，无需拉起整个 solve_service。`solve_comprehensive` 仍然内部管理 CalcContext 生命周期，保持 3 趟评估的性能优化。


## 六、风险评估

| 风险点 | 严重度 | 缓解措施 |
|--------|--------|---------|
| 重构引入计算结果偏差 | 高 | 重构前后用相同输入对比结果，性能测试基线 test_perf_solve.py |
| 缓存行为变化导致性能退化 | 中 | CalcContext 保持相同的缓存命中逻辑，逐步验证 |
| 函数签名变更量大 | 中 | 分步骤渐进重构，每步独立验证 |
| 反向依赖消除影响 batch_optimizer | 低 | _build_batch_details_list 逻辑独立，下移无副作用 |

## 七、总结

当前求解器的**业务逻辑和性能优化是正确的**，但**状态管理架构存在结构性债务**：

1. Scenario 被寄生变异 → 无法序列化、无法独立调用
2. 缓存传递隐式 → 数据流不可追踪
3. 层级反向依赖 → 计算函数无法脱离 service 层
4. CombinationResult 混合中间态和最终态 → 数据流不透明

重构的核心是：**将缓存从 scenario 剥离到 CalcContext，由 Service 层显式管理**，使计算层变为无状态纯函数，为 MCP 封装和 Agent 调度架构奠定基础。
